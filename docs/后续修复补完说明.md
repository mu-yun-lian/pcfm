## 三、「SQLite 成为真相源」未落地的详细原因

这是本次最重要、也最需要讲清楚的一点。结论是：**不是没做，而是做了之后实测发现不安全，主动回退了。**

### 1. 当前架构：SQLite 是「写后同步的镜像」，不是真相源

- 业务真相数据仍写在 JSON 文件里（conversation_sources.json、conversation_versions.json、conversation_state.json、会话文件等），由 ConversationWorkbench 内部的 _write_json 完成。
- SQLite 的 person / source / version / session / message / conversation_state 表，是靠「服务层在特定方法之后调用 _sync_*_to_sqlite」把 JSON 内容镜像进去的。
- 也就是说：**真相在 JSON，SQLite 是 JSON 的快照副本**。

### 2. 镜像同步没有覆盖所有写路径

同步函数只在少数服务层方法之后被调用（review_conversation_source、review_conversation_response_candidate、review_optimization_candidate、review_optimization_style_candidate、rollback、send_message、会话 CRUD 等）。

但 ConversationWorkbench 内部还有若干「直接改 JSON、却不经过这些服务层方法」的路径，例如：

- merge_source_entity_aliases —— 合并实体别名时，可能使已有版本失效，直接改 conversation_versions.json 的 validation_status（写成 invalidated_evidence_contract）。
- migrate_evidence_contract —— 证据契约迁移，直接改 JSON。
- 其他散落的 _write_json 调用。

这些路径改完 JSON 后，SQLite 镜像不会立即更新，于是**镜像落后于 JSON**。

### 3. 切读路径后，真实复现了「读到旧数据」

我做了实验：新增 _list_versions，优先从 version 表（data 列）读，JSON 只在 SQLite 为空时回退。结果全量回归出现：

- 1 个 failure：某版本 JSON 里 validation_status 已被改成 invalidated_evidence_contract，但 SQLite 镜像还是旧值 exploratory_source_integrity_passed_accuracy_not_assessed，读路径读到了旧值，断言失败。
- 4 个 error：读路径触发了更多 SQLite 连接，测试里未 close() 的第二个服务实例泄漏了 pcfm.db 文件锁。

这正好证明了担忧：**只要镜像可能陈旧，把读切到镜像就会返回错误数据**。因此我把读路径回退，恢复「JSON 是读真相源」。

### 4. 结论

要把 SQLite 真正变成真相源，正确顺序是：

1. 先做「写路径全量审计」：把每一处会改 conversation 数据的 _write_json 都收敛到「写 JSON + 同步 SQLite」的统一入口（最好在同一个事务里）。
2. 再切读路径：Repository 读 + JSON 回退 + 一致性校验。

当前阶段只完成了第 1 步的一小部分（版本 + 状态的原子写），第 1 步本身没做完，所以第 2 步（读路径）不能安全上线。这正是方案文档里把「第二步」标为「后续迭代、不纳入本次验收」的原因——它需要谨慎的写路径收敛，不适合在连续自动化节奏里仓促完成。
