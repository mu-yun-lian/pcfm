## 二、逐项修复详情

### R1（Critical）停止生成实际不生效

**问题**：JobRunner.cancel() 只调用 event.set()；send_message 任务传入的 lambda 忽略 cancel/progress；消息流水线内部不检查取消。用户点击「停止」后任务仍跑到完成并标记 succeeded。

**修复**：
- message_pipeline.send_message 新增 cancel_event / progress 参数，定义 _check_cancel()，在方法开头与两处持久化前调用，命中即抛 JobCancelled。
- 用户消息在 append 后立即 _save_active_messages（取消后刷新仍保留用户消息）。
- webapp.py 的消息任务 lambda 改为把 cancel 事件透传给 send_conversation_message；conversation_service 再透传给 send_message。
- _conversation_call 只捕获 ConversationError，JobCancelled 正常上抛，由 JobRunner 标记 cancelled。

**验证**：预置 cancel_event 时 send_message 抛 JobCancelled；未预置时正常返回 answered。

### R2（Critical）单条「提取候选」不等待任务

**问题**：extractSource 调用后端返回 job_id 后立即 refreshConversation 并提示「候选已生成」，但后台任务可能刚排队。

**修复**：extractSource 改为先 pollJob(job_id) 等待任务成功，再 refreshConversation 与提示。

### R3（High）全局锁残留、长任务未完全异步

**问题**：conversation_service 的 summary/会话/现实对照/优化、source_service 的 add/review 均用 self._lock（全局锁）；URL 采集（15s）与 25MB 文件解析都在全局锁内。

**修复**：将上述按人物作用域的方法全部改为 self._person_lock(person_id)（conversation_service 12 处、source_service 4 处、version_service 1 处），消除跨人物阻塞；create_conversation_person 保留全局锁（新建人物）。

### R4（High）SQLite 只覆盖 person/job

**问题**：session/message/source/version 四张表只有 schema，无 repository；核心数据仍走 JSON。

**修复**：
- 新增 persistence/repositories/source_repo.py（SourceRepository.upsert/count/clear）与 version_repo.py（VersionRepository）。
- application.py 创建 source_repo / version_repo，并新增 _sync_sources_to_sqlite / _sync_versions_to_sqlite（读 JSON 镜像到 SQLite，失败不影响主流程）。
- source_service 的 add_text/file/url/review 之后同步 source 表；version_service 的 rollback 之后同步 version 表。
- migrate_to_sqlite.py 迁移与 rollback 均补齐 source/version。

**说明**：本次为「元数据镜像写透」，JSON 仍为数据真相、文件大对象未迁库；「版本创建跨文件事务」仍属后续工程。

### R5（High）request_id 未透传前端

**问题**：api() 抛错时丢弃 500 响应里的 request_id。

**修复**：api() 从响应体读取 request_id，错误信息附带「（错误编号：xxx）」。

### R6（High）conversation 数据损坏仍致 500/启动失败

**问题**：conversation/_shared.py 的 _read_json 用裸 json.loads；启动迁移只捕获 ProductError。

**修复**：_read_json 改用 data_errors.safe_read_json，并把 PcfmDataError 转为 ConversationError；application.py 启动迁移的 except ProductError 改为 except Exception（单人物任何损坏都不阻断启动）。

### R7（Medium）模型请求无重试/退避

**问题**：_json_request 对 HTTPError/网络错误直接抛错；invoke 只对空 content 重试。

**修复**：_json_request 对 429/500/502/503/504 与 URLError/TimeoutError/OSError 重试 1 次（退避 0.5s）；401/404/405 与 JSON 解析错误不重试。

### R8（Medium）list_people 过度宽泛 except Exception

**问题**：except Exception 把编程错误（KeyError/TypeError）也伪装成「数据损坏」。

**修复**：窄化为 except (ProductError, ConversationError, PcfmDataError, CognitiveWorkbenchError)。

### R9（Medium）pollJob 无超时、启动不清旧任务

**问题**：pollJob 只有成功/失败/取消三个退出条件；后端启动不清理上次进程遗留的 queued/running。

**修复**：pollJob 加 10 分钟超时（超时抛「任务超时，请重试」）；JobStore 新增 recover_stale()，在 main() 启动时把 queued/running 标记 failed（DB 文件不存在则跳过，保持懒连接）。

### R10（Medium）状态码中文映射不完整

**问题**：labels.ts 未覆盖 content_contract_gate_failed_bounded_anchor 等 6+ 个终态，未映射值显示「处理中」。

**修复**：补齐 11 个状态的中文映射（含 source_verbatim_person_style、not_run_no_person_prediction、unified_gate_failed 等）；未映射兜底从「处理中」改为「未知状态」，并同步更新 vitest 断言。

### R11（Medium）light=True 仍读全量 JSON

**问题**：summary(light=True) 仍 _list 读取全部 sources/messages/versions/optimization_candidates。

**修复**：light 模式下 versions 与 optimization_candidates 直接置 []，sources 公共视图置 []（仍统计 source_counts 与读取会话消息）。

### R12（Low）DPAPI 跨平台 / 旧前端残留 / 模型路径兼容

记录为延迟：DPAPI 仅 Windows（当前用户环境为 Windows，可用）；app.js 与 index.legacy.html 保留作为未构建 dist 时的回退参考；模型列表路径兼容需按具体端点逐一验证。
